# 存储架构改向（应用级单库 + 独立向量库）

Type: grilling
Status: resolved
Assignee: agent
Blocked by: 06, 14, 15, 20

## Question

原设计「一个存档 = 一个 .sqlite 文件、拷贝即分享」在评审中被推翻。需要重新拍板存储架构：

① 库的边界：所有存档进一个 SQLite，还是继续分文件？故事书与存档是否同库？
② 向量索引放哪：SQLite BLOB vs DuckDB（独立文件 / attach / 内存重建）？
③ 关键词检索：SQLite FTS5 vs DuckDB BM25？
④ 导出/分享：单存档怎么带走？导入如何分配身份？
⑤ 新原点归档：单库下旧日志去哪？
⑥ 并发与备份：单写 WAL、整库备份、崩溃恢复。

## Answer

**决议（设计复审 2026-09-09 拍板）：**

### ① 库边界 = 应用级单库

- **一个 SQLite 文件**（app 数据目录 `octopus.db`，WAL）承载：故事书（released/draft）、存档 meta、命令日志、快照、维护历史、归档表。
- 存档相关表按 `save_id` 分区；故事书按 `storybook_id`。**不再一存档一文件**。
- 好处：跨存档查询/统计、故事书与存档同库事务、备份简单；代价：单存档分享需导出（见 ④）。

### ② 向量索引 = 独立 DuckDB 文件

- DuckDB 文件（如 `octopus-vectors.duckdb`）只放 embedding 与检索索引，**派生、可重建**，不参与权威（#06：索引非权威）。
- 不采用 attach SQLite / HNSW 持久化（评审排除，实现风险高）。事件量增长时再评估 HNSW。

### ③ 关键词检索 = SQLite FTS5

- 权威库内置 FTS5，DuckDB 只负责向量；终结 #06 与 #05 的 FTS5/BM25 之争。

### ④ 导出 / 导入 = 抽单存档包

- 导出：从共享库抽出该存档（内嵌冻结模板 + 该存档命令日志/快照/维护历史/归档）为**独立 `.sqlite` 包**，仍满足「分享一个自包含文件」的产品诉求。
- 导入：读入包并**分配新 `save_id`**（不覆盖同 id）；带「新导入」标记（#21）。
- 整库备份 = 直接拷贝 `octopus.db`（可选一并拷向量库，或导入后重建）。

### ⑤ 新原点归档 = 库内归档表

- 旧日志写入 `archived_commands`（按 `save_id` 分区、只读标记），回放/回滚上限 = 新原点；不再「挪出为独立文件」。

### ⑥ 并发 / 备份 / 恢复

- 单用户单写者：SQLite WAL + 串行命令管线（#06/#24），不做多写并发。
- 备份 = 整库拷贝；单存档迁移 = 导出包。
- 崩溃恢复 = WAL 重放 + 命令日志重放；快照仍只是启动加速缓存。
